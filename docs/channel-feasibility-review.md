# PRD 审查与消息渠道可行性备忘

- 审查日期：2026-10-07；依据：`docs/PRD.md` v1.1。
- 状态：讨论稿，建议未获用户批准；未修改 PRD，未完成任何真实渠道接入。
- 计划：`docs/plans/2026-10-07-prd-channel-feasibility.md`。
- 本文区分官方规则、仓库事实与产品建议；条款适用性须由 Meta/BSP 确认，必要时请专业法律顾问评估。

## 1. 审查结论（按优先级）

### P0：AI 用途资格需要独立上线闸门
- 位置：PRD 11–19、87–95、507–514、531–543 行。
- 已有：定位是商户特定订单助手，并非通用聊天机器人；已有模型数据最小化与不默认允许训练的约束（第 7.2 节）。
- 官方事实：Meta 平台条款（2026-09-23 修订）§4.7 对 AI Providers 将 AI 技术作为主要而非附带功能提供的情形设限，存在指定国家例外；同时允许商户聘用 AI Provider 作为 Solution Provider，并限制平台数据用于训练/改进模型。[S1]
- 缺口：没有本产品用途、运营主体与服务商角色适用性的确认记录。不能因名称含 AI 就断言被禁，也不能因是电商客服就断言自动豁免。
- 建议：上线前明确订单/商品客服边界、账号归属、模型供应商数据用途与合同安排，取得适用性确认；不确定时阻断真实自动发送。改名不是规避规则的办法。

### P1：账号“可用”不等于我们的接入路径已成立
- 位置：PRD 16、87–95 行。
- 已有：首发限定已有可用 Business Platform 账号的商户，并要求核验已有客户端能否共存。
- 官方事实：符合条件的 WhatsApp Business App 商户可通过 Embedded Signup 的官方 Coexistence 路径继续使用 App，同时接入 Cloud API；接入方需满足 Solution Partner 或 Tech Provider 等前置要求。[S3]
- 缺口：未列出首家试点的账号资产、授权方式、现有服务商解绑/迁移条件、计费账户与接入方资质证据。
- 建议：第一家试点先选已有可用平台账号的商户。只有 Business App 的商户另走共存资格验证，不能与现有首发客群混算。官方共存不等同于非官方扫码方案。
- 版本提醒：官方共存文档提示 Embedded Signup v2/v3 于 2026-10-15 弃用；若实现嵌入式注册，应核验 v4，不照搬旧教程。[S3]

### P1：当前成本需要版本化账单验证
- 位置：PRD 280–339、522 行。
- 已有：产品 Credits 与 Meta/BSP 费用分账，后者由商户承担；没有把产品 24h 窗口当成 Meta 统一会话收费。
- 官方事实：当前价格按消息类别、接收方市场与送达计量；2026-10-01 起普通 service 消息每号码每月前 1,000 条免费，超额收费。AI Providers 另有 service 定价政策，不直接套用普通免费额度。[S2]
- 缺口：账号实际分类、有效付款方式、印尼当前费率及 BSP 加价没有真实账单测算。商户承担通道费仍影响采用率，不能只看本产品毛利。
- 建议：分别记录产品服务费、Meta/BSP 账单、模型和基础设施成本。覆盖低/中/高消息量，用实际送达类别和价格版本核算；没有证据不承诺“窗口内全部免费”。
- 待核验：本轮抓取摘要对窗口内 utility 的新旧规则呈现不一致，不将此细项定价写死；上线前以生效费率卡、官方说明和实际账单核对。

### P2：多渠道会改变触达与计费，不是加几个入口
- 位置：PRD 34–46、163–179、280–298、547 行。
- 官方事实：普通 Telegram bot 不能主动开启与从未互动用户的私聊；sendMessage 成功返回 Message，不是 WhatsApp delivered/read 同语义回执。[S4][S5]
- 推论：WooCommerce 电话号码不能直接转换为可联系的 Telegram 买家；已有 WhatsApp 同意也不能默认延用到另一渠道。
- 建议：扩展前单独定义身份绑定、渠道同意、人工接管、未知状态、重试与 Credits 口径。不要把 Telegram 发送成功映射成已送达来扣费。

## 2. WhatsApp 可行性与接入路线

结论：官方 API 有技术实现路径；本产品的商用资格、具体账号能力和经济性仍是有条件可行，未完成实证。

| 路线 | 建议 | 验证门槛 |
| --- | --- | --- |
| 现有平台账号 + Cloud API | 首家试点优先 | 商户授权、账号/号码资产、Webhook、模板、付款方式、AI 用途判断 |
| 经现有合规服务商接入 | 可评估的替代实施路径 | 费用、数据访问、账号所有权、回执能力、退出迁移；服务商不替代用途合规 |
| Business App 官方共存 | 单独验证，不默认纳入首发 | 接入方资质、号码资格、注册版本、人工消息同步与自动化暂停 |
| Baileys / WPPConnect | 不作为首发或官方故障备用 | 沿用 PRD 的研究边界，不绕过账号/政策限制 |

先跑通“1 家商户、1 个号码、1 个非 COD 催付流程”，再扩大到 3–5 家。先验证订单→发送资格→模板→回执→回复/人工接管→付款停发；COD 和正式链上收费按原 PRD 独立验收，不能把缩小试点当作修改首版承诺。

## 3. 渠道范围建议（待用户决策）

| 渠道用途 | 建议决策 | 原因/重新评估条件 |
| --- | --- | --- |
| WhatsApp 买家沟通 | 首发唯一消息渠道，有条件推进 | 与当前 PRD 客群一致；先通过资格和真实闭环验证 |
| Telegram 买家沟通 | 不进入首发；验证后扩展候选 | 尚无买家实际使用、bot 会话和订单绑定证据，触达/计费需独立设计 |
| Telegram 商户通知 | 单独收集需求，暂不承诺 | 通知商户处理异常，不等于 Telegram 买家客服；需控制订单隐私 |
| LINE / Messenger / Instagram 等 | 暂不纳入 | 每次只选择一个有付费需求证据的渠道；本轮未核验这些平台的接入政策 |

建议扩展触发门槛（产品建议，不是平台规定）：完成 PRD 要求的 10 家访谈后，至少 3 家愿意参与新增渠道试点，并提供真实买家会话/绑定路径；能测量相对 WhatsApp 的新增可触达订单；完成独立授权、成本、计费和客服验收。

只保持发送、入站事件、回执与能力判断的清晰边界，不提前开发通用多渠道平台。电商平台扩展（例如 Shopify）与消息渠道扩展是两条独立路线。

## 4. 最小真实试点测试样例

以下用例仅完成设计审查，全部尚未执行；不是已通过的集成测试。执行需先获得账号授权和适用性确认。

| ID | 类型/输入与步骤 | 预期结果 |
| --- | --- | --- |
| C1 | 正常：合格商户、有效同意、获批模板、非 COD 待支付订单，到第 15 分钟触发 | 复查后发送；保存平台 ID；收到首次 delivered 后按 PRD 记一笔产品 Credit，另记通道成本 |
| C2 | 边界：只有电话号码，无可核验同意，触发提醒 | 安全抑制，不发送、不扣产品 Credit；保存原因 |
| C3 | 边界：买家最后入站已超过 24h，尝试自由文本回复 | 不直接发送自由文本；只有满足资格的获批模板才可发送，否则转人工 |
| C4 | 异常：平台受理后请求超时，再重复/乱序投递 delivered 回调 | 不盲目重发；按消息唯一标识去重；不重复扣产品 Credit |
| C5 | 竞态：排队期间付款/退订/人工接管，再执行任务 | 发送前复查并停止；已提交消息明确标记无法召回，不伪报撤回 |
| C6 | 异常：模板暂停、授权失效或账单支付方式失效 | 停止受影响流程、通知商户；不切换非官方或未授权渠道 |
| C7 | 计费边界：普通 service 号码本月第 1,000/1,001 条送达；另测 AI Provider 分类 | 按各自生效规则核账；不误套免费额度；不得混同产品 Credit 窗口 |
| C8 | 条件测试：若选官方共存，在 App 人工发消息并触发自动任务 | 依据实测事件同步和接管机制防重复回复；无法保证则不开放共存自动化 |
| C9 | Telegram 边界：只有订单手机号，用户未与 bot 建立会话 | 不宣称可主动触达；用户建立会话并安全绑定订单后再验证权限 |
| C10 | Telegram 语义：sendMessage 返回成功，无送达/阅读证据 | 只标记发送成功；不套用 WhatsApp delivered 计费或阅读统计 |

## 6. 需要讨论的决定

首先确认：能接触到的首批商户已经拥有可用 WhatsApp Business Platform 账号，还是只在手机上使用 WhatsApp Business App？

其次确认是否采纳“WhatsApp 单渠道首发、Telegram 等渠道验证后再扩展”。若实际客户与 PRD 假设不同，先修订客群和接入路线，不为技术上容易实现而扩平台。
