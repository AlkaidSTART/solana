# WhatsApp 接入方式指南

- 整理日期：2026-10-07；面向 SolaFlow AI 的选型和试点准备。
- 状态：文档交付，不代表已取得 Meta 资质、商户授权或完成真实接入。
- 产品边界以 [PRD](PRD.md) 为准；背景见 [渠道可行性审查](channel-feasibility-review.md)。本文建议不自动变更 PRD。
- 执行记录：[计划](plans/2026-10-07-whatsapp-integration-guide/plan.md)、[结果](plans/2026-10-07-whatsapp-integration-guide/result.md)。

## 1. 先区分三个维度

| 维度 | 含义 | 与其他方式的关系 |
| --- | --- | --- |
| Cloud API | 官方收发消息通道，入站消息和发送状态通过 Webhook 接收 | 是本项目首版消息通道 [S1] |
| Embedded Signup | 商户登录、选择资产并授权应用的入驻流程 | 可与 Cloud API 组合，不是替代消息协议 [S2] |
| Tech Provider / Solution Partner / BSP | 接入主体、合作伙伴及服务商安排；不同服务商可能代理接口和结算 | 可以提供前两项的封装，不能替代商户授权和用途审查 [S2][S4] |

WhatsApp Business App 是商户使用的手机应用，不等于已具备可供我们调用的 Business Platform 账号。官方 Coexistence 支持符合条件的 App 商户保留原号码和 App 使用方式，同时接入 Cloud API；不能据此承诺所有现有号码都支持。[S3]

## 2. 选型速查

以下为项目建议，不是平台保证：

| 商户情况 / 目标 | 接入组合 | 本项目取舍 | 先确认什么 |
| --- | --- | --- | --- |
| 已有可用 Business Platform 账号 | 商户正式授权 + Cloud API，试点可人工协助配置 | 首家试点优先 | 资产控制权、权限、现有服务商、Webhook、计费 |
| 希望商户在产品内自助入驻 | Cloud API + Embedded Signup | 后续产品化路径 | Tech Provider 路径、App Review、advanced access |
| 仅有 Business App，希望保留原号及 App | Embedded Signup 的官方 Coexistence 流程 | 单独验证，不默认纳入首发 | 接入方和号码资格、地区、版本、同步限制 |
| 已使用服务商或希望减少接入运维 | 经合规服务商接入 | 可选替代实施路径 | 官方授权链、费用、回执、资产归属和退出迁移 |
| 希望用非官方扫码快速上线 | Baileys / WPPConnect 等研究方案 | 不用于正式首发，也不作为官方故障备用 | 沿用 PRD 的研究边界，不承诺官方支持 |

**推荐顺序：** 先验证一家符合 PRD 的印尼 WooCommerce 商户，再决定是否投入自助授权；不要为了接入第一家商户同时建设多个渠道。

## 3. 路径 A：已有平台账号，直连 Cloud API

### 前置条件
- 商户能证明并授权使用目标业务资产和号码；盘点现有 App、服务商和消息处理系统。
- 明确调用主体：商户自有应用，还是 SolaFlow 应用代表外部商户操作。官方起步示例不意味着 SaaS 可绕过对外服务审核。[S1][S2]
- 具备可接收 HTTPS Webhook 的后端、凭证保管能力和测试收件人；生产凭证及权限按实际授权模式配置。[S1]

### 操作步骤
1. 建立资产清单：Business Portfolio ID、账号 ID（接口中的 `waba_id`）、`phone_number_id`、App ID、资产所有者、现有服务商、账单支付方。
2. 在 Meta App 的 WhatsApp 配置中确认资产关联；使用官方测试资产和测试收件人先验证收发，不直接操作生产买家。[S1]
3. 由资产管理员通过正式权限机制授权。不要要求商户共享个人登录密码，也不要通过聊天或工单传递生产 token。
4. 将适用的生产凭证加密保存到后端，核对权限范围；临时测试 token 不用于生产，“持久”凭证也要考虑撤销与轮换。[S1]
5. 配置 Webhook 验证、事件订阅、租户路由和消息状态处理；不要直接覆盖现有生产订阅而导致旧系统失联。
6. 确认模板、付款方式、账号状态和消息规则，通过第 8 节用例后再小范围启用自动化。

### 限制与费用
- “人工协助配置”只是试点操作方式，不是免审核或免授权方案；存在现有 BSP 时先确认是否可直连、是否需迁移。
- 本项目按 PRD 要求由商户承担其 Meta/BSP 通道账单；若实际模式要求我们代付，必须先重新审查成本和价格条款。
- 暂不承诺迁移无中断、历史消息自动完整导入或所有原客户端可共存。

## 4. 路径 B：Cloud API + Embedded Signup

### 前置条件
- 为外部商户提供接入前，核验接入主体资格、业务验证及所需权限的 App Review / advanced access；重点包括 `whatsapp_business_messaging`、`whatsapp_business_management`。[S2][S4]
- 准备正式域名、隐私政策、数据删除流程、产品演示和权限用途说明；最终材料以审核入口要求为准。

### 操作步骤
1. 按官方指南配置 Facebook Login for Business 和 Embedded Signup，在产品中提供“连接 WhatsApp”。[S2]
2. 商户登录、选择或创建资产、确认号码并授权；用户取消或授权失败时保留未连接状态。
3. 前端将流程返回的 code 和资产标识交给后端；后端校验发起会话与商户身份，交换客户范围的业务 token，重新核验资产归属后绑定租户。[S2]
4. 标准 Cloud API 入驻按流程完成必要的号码注册及账号 Webhook 订阅；**Coexistence 号码已注册，不照搬标准注册步骤**。[S2][S3]
5. 核验付款安排，完成连通性和撤销授权测试后才展示“可用”。不是 Solution Partner 或没有相应伙伴安排时，商户需补充账号付款方式。[S2]

### 版本和资产模型提醒
- 官方提示 Embedded Signup v2/v3 将于 **2026-10-15** 弃用；新实现应核验 v4，不能直接采用旧教程。[S2]
- 官方正在测试 WAAC / Messaging Account 分拆；`waba_id` 在新模型中表示 Messaging Account ID。该能力仍为 beta，实施时再次核验。[S2]
- 不混用 `business_id`、`waba_id`、`phone_number_id`；标准入驻与共存的账号生成/共享规则不同。[S2][S3]
- OAuth 成功不等于消息通道已可用；仍需完成权限、订阅、号码、模板与计费检查。

## 5. 路径 C：Business App 官方共存（Coexistence）

适用于目前只使用 WhatsApp Business App、希望保留原号码和人工操作的商户；这与 PRD 首发“已有可用 Business Platform 账号”的客群不同。[S3]

### 前置条件与步骤
1. 核验接入方的 Tech Provider / Solution Partner 等资格，以及商户 App 版本、号码、地区和账号适用条件；不得只凭手机号判断可用。[S3]
2. 配置官方共存入驻流程，由商户在官方界面完成验证和授权；不要先删除原 App 账号或擅自迁移号码。
3. 按共存的专属后续步骤配置订阅、所需同步和连接状态；聊天历史分享须尊重商户选择。[S3]
4. 单独测试 App 人工消息同步、重复事件、断连和恢复，确认不会触发机器人与人工重复回复。

### 限制与费用
- 官方支持 App 一对一消息与 API 协同，但同步范围和功能限制须按官方当前说明核验，不承诺无损复制所有历史数据。[S3]
- 共存不等于 Baileys 扫码，也不自动免除 API 消息费或服务商费用。
- 项目建议：人工消息识别和自动化暂停未验证前，不向这类商户开放生产自动回复。

## 6. 路径 D：通过服务商接入

此处 BSP 泛指提供官方平台接入服务的服务商；签约前须核验其实际 Meta 合作伙伴身份、授权链和接口模式，不仅凭营销名称判断。[S4]

### 准备及落地步骤
1. 确认商户资产归属、管理员权限、现有合同和退出条件。
2. 获取服务商的接口、授权、Webhook、状态回执、模板、限流和价格文档；确认是代理 API 还是直接调用 Meta。
3. 按服务商正式流程授权；若它封装 Embedded Signup，仍核验账号、权限和付款安排。
4. 将服务商事件映射到内部状态，跑相同安全与业务测试，再与实际账单核对。

### 采购与迁移检查表
- 费用：Meta 通道费、服务商加价、月费、号码费及其他收费是否分列；谁开票、谁付款。
- 数据：保存位置、保留期限、子处理方、删除机制、能否导出。
- 能力：入站消息、送达/失败回执是否齐全；不能把“请求成功”当作“已送达”。
- 退出：号码和账号是否归商户、模板与历史数据能否迁移、解绑权限、停机窗口和支持响应。
- 若服务商要求我们承担通道账单，先调整商业方案，不能默认沿用 PRD 的商户自付模式。

## 7. 本项目统一实现与上线闸门

以下是依据 PRD 的实现要求，**不是已实现能力**：

- **账号绑定**：首版一个业务号码只绑定一个店铺；后端以已核验资产映射租户，不能信任前端传入的任意账号 ID。
- **安全**：凭证仅保存在服务端并加密；Webhook 按相应官方/服务商规范验签，验证挑战和事件验签分开处理；日志脱敏。
- **事件处理**：验签、持久化/可靠入队后及时响应；重复与乱序回执不重复执行副作用，不将发送 HTTP 成功认定为送达。
- **发送资格**：检查同意用途、模板批准状态、账号连接、订单状态、额度、频次和人工接管。订单电话不等于营销同意。
- **窗口**：自由形式回复受最近买家消息开启的 24 小时服务窗口约束；主动提醒仍执行 PRD 的同意和模板要求。[S1][S5]
- **停止条件**：退订、付款、取消、发货、暂停、授权撤销或人工接管后停止不适用任务；不能承诺撤回已提交平台的消息。
- **计费**：产品 Credits 窗口与 WhatsApp 服务窗口分开；未知送达状态不盲目重发或直接释放额度，按 PRD 进入复核。
- **AI 用途**：依据前次审查，产品用途、主体角色、模型数据使用及条款适用性仍需确认；不得直接断言订单助手天然获准或被禁止。[S6]
- **价格**：按生效费率、市场、类别、实际账号适用政策和 BSP 账单测算；不在本指南写死印尼费率，不承诺窗口内全部免费。[S7]
- **退出与回滚**：提供店铺级停止开关；断连先停自动化，记录未决发送，再按授权撤销/解绑流程处理，不自动切换非官方协议。

### 试点前必须准备的证据
- [ ] 一家符合 PRD 的印尼 WooCommerce 商户、一个号码、测试收件人及同意记录。
- [ ] 账号类型、资产归属、实际授权模式、接入主体资格及现有服务商处理方案。
- [ ] 有效计费安排、模板、消息类别、当前费率及服务商额外费用。
- [ ] AI 用途及数据处理适用性确认、凭证保管和撤销方案。
- [ ] 完成开发环境测试和受控实号测试，有脱敏事件记录、消息 ID、实际结果与账单依据。

## 8. 对应测试样例

**下表全部是待实施测试设计，真实接入测试未执行。** 实施时记录环境、时间、输入、预期、实际、脱敏证据和负责人；模拟成功不能代替实号验收。

| ID / 类型 | 输入与操作 | 预期结果 |
| --- | --- | --- |
| WA-01 正常 | 已授权测试商户和号码，核验账号、订阅与付款配置 | 资产归属和店铺绑定正确；凭证不返回前端 |
| WA-02 正常 | 同意有效、获批模板、符合 PRD 的非 COD 待支付订单；接收 delivered 回执 | 一次有效提醒；按 PRD 建立 Credits 窗口，不按 HTTP 成功提前结算 |
| WA-03 正常 | 测试买家主动回复，再在服务窗口内发送自由形式回复 | 入站归属正确；窗口基于买家消息更新 |
| WA-04 边界 | 距最后买家消息分别为 23:59:59、24:00:00，提交前再次检查 | 达到到期时按窗口已关闭处理，不绕过模板/同意要求 |
| WA-05 边界 | 同一号码绑定第二店铺；用租户 A 访问 B 的账号 ID | 拒绝绑定或访问，无跨租户数据泄漏 |
| WA-06 边界 | 重复、乱序投递同一消息的状态事件 | 不重复扣 Credits，不回退终态，不产生重复任务 |
| WA-07 异常 | 伪造 Webhook 签名或未知号码事件 | 拒绝非法事件；未知归属进入排查，不写入任意租户 |
| WA-08 异常 | 商户取消授权、撤销 token、缺权限或模板被拒 | 未连接/不可用状态清晰；停止自动发送，提供修复原因 |
| WA-09 异常 | 发送超时、限流、5xx；缺少明确发送终态 | 区分可重试失败与结果未知；未知状态不盲重发，重试有上限 |
| WA-10 边界 | 提交前发生退订、付款或人工接管；另测提交后停止 | 前者阻止发送；后者如实记录已提交，不声称撤回成功 |
| WA-11 共存专项 | App 人工发消息、同步重复事件及暂时断连 | 人工接管规则生效，不与自动回复冲突；断连时安全停止 |
| WA-12 费用核对 | 受控实号试点，记录消息类别、送达、费率版本和账单 | Meta/BSP 费用与产品 Credits 分账，可解释差异 |

最小试点闭环建议：连接 → 创建符合条件的测试订单 → 模板提醒 → 送达回执 → 买家回复 → 人工接管或付款停止 → 对账 → 断连。仅此闭环通过后再扩商户；Embedded Signup、共存各自作为独立小 MVP。
