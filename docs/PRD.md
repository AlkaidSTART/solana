- 文档版本：v1.2
- 修订日期：2026-10-07
- 文档状态：开发与内测规格草案；平台接入、商业价格和业务效果须通过本文定义的验证门槛。

## 1. 产品定位与首发范围

### 1.1 产品概述

- **产品名称**：SolaFlow AI（暂定）。
- **产品形态**：Web SaaS 工作台、订单自动化与多语言会话引擎、Solana Pay 服务费充值中心。
- **长期客群**：中国出海东南亚的电商卖家，以及印尼、泰国、越南、马来西亚、菲律宾、新加坡的本地中小商户。
- **首发客群**：经营印尼市场 WooCommerce 独立站、已有可用 WhatsApp Business Platform 账号、愿意提供订单与履约反馈的中小商户。
- **首发语言**：印尼语、英语。中文用于商家工作台；泰语及其他市场语言在后续验证后加入。

产品帮助商户处理待支付订单提醒、COD 收货意愿确认和买家咨询，并把异常交给人工。Solana Pay 用于商户购买本产品的订阅和 Credits；买家的商品付款仍在商户原有电商渠道完成，COD 仍按商户原有物流流程收款。

### 1.2 首版价值与边界

| 价值 | 首版交付行为 | 衡量方式 |
| --- | --- | --- |
| 减少待支付订单流失 | 对符合授权条件的非 COD 待支付订单，在创建满 15 分钟后发出提醒，发送前复查订单 | 提醒后支付率、与对照组的增量差异 |
| 减少 COD 发货前信息缺口 | 记录确认、改址申请、取消申请、联系失败和超时结果，交给商家决定履约 | 确认率、取消率、履约结果、误判反馈 |
| 覆盖夜间咨询 | 在可回复窗口内回答商品与政策问题，超出能力边界时进入人工队列 | 首次响应时间、正确率、人工处理时长 |
| 提供链上服务费支付 | 使用 USDC 购买订阅或 Credits，支付结果可核查，重复通知只入账一次 | 有效转账入账成功率、到账耗时、异常率 |

首版提供规则判断和证据展示，不宣称能验证地址真实性或预测恶意弃单。不自动取消订单、修改地址、退款、发货或生成未经批准的折扣。

| 功能 | 首版 | 后续扩展或条件 |
| --- | --- | --- |

## 2. 用户、业务假设与指标

### 2.1 用户角色与核心任务

| 角色 | 核心任务 |
| --- | --- |
| 商户所有者 | 绑定店铺与 WhatsApp，设置规则和预算，购买服务，查看效果与异常 |
| 商户管理员 | 管理工作流、知识库、成员和人工队列；不能处理平台级资金复核 |
| 客服 | 处理分配给自己的会话、改址和取消申请，记录商家在原平台的操作结果 |
| 财务 | 查看本租户充值、扣费与订阅流水，发起充值和异常付款申诉 |
| 买家 | 接收已同意的消息、咨询商品、确认 COD、提出改址或取消、退订 |
| 平台运营与财务复核人员 | 排查接入和支付异常；访问业务数据须有授权并留下审计记录 |

### 2.2 待验证的业务假设

夜间咨询流失、俚语理解困难、COD 拒签损失和跨境服务费支付障碍是访谈与内测的研究方向。原稿中的“15%～25% 拒签”“3%～5% 支付费率”“20:00～01:00 最活跃”缺少来源，本版不把它们作为已知市场事实。

首批访谈至少覆盖 10 家符合首发条件的商户，采集现有工作方式、每月订单量、真实消息费用、履约损失、收款方式及使用 USDC 的意愿。每项结论记录样本、时间、数据来源和缺失项；没有证据时显示“未验证”。

### 2.3 KPI 口径

以下均为内测目标，不是已实现的业绩或销售承诺。

| 指标 | 计算口径与观察窗口 | 初始目标 |
| --- | --- | --- |
| 提醒组支付率 | 在发送资格检查时仍待支付、且进入提醒组的订单中，24 小时内完成付款的订单比例；未送达订单仍保留在分母中 | ≥15% |
| 净支付率 | 同一批符合条件的提醒组订单中，24 小时内付款且付款后 7 天未取消或退款的订单数 / 该组订单总数；未完成观察窗口的样本显示观察中 | 与毛支付率同时报告 |
| 催付增量效果 | 同口径提醒组支付率减去对照组支付率，按店铺、国家、订单金额分层 | 差值为正；报告样本量和置信区间 |
| COD 拒签率 | 已结束履约订单中的明确拒签数 / 已签收及所有已结束未签收订单数；无法联系、地址问题、取消和未发货另列 | 相比同口径基线下降 5～8 个百分点 |
| 试用付费转化率 | 完成店铺和通道启用的试用商户中，试用开始后 30 天内完成首次真实订阅付款的比例 | ≥25% |
| 次月付费留存率 | 首个付费周期到期后 7 天内续费的商户数 / 已完整观察到该时点的首付商户数 | ≥80% |

催付试验按店铺内买家稳定分组，默认保留 20% 对照组。两组使用相同的资格判断；对照组仅不执行本产品的催付，原有商家营销动作须记录。订单付款按原平台订单或 checkout 关联结果确认，点击短链不计为付款。付款事件缺失时显示数据不完整，不推断成功。

COD 效果同时展示发货前取消数、未发货数及总履约成本，避免仅通过减少发货来制造拒签率改善。达到观察窗口的样本不足时，只报告当前数据，不宣布目标达成。

## 3. 核心流程、工作台与架构

### 3.1 商户首次使用流程

1. 注册并创建租户，设置首发市场、店铺时区和人工服务时间。
2. 验证店铺归属，完成最小必要 API 权限授权、Webhook 验签及真实样例接收。
3. 绑定商户自己的 WhatsApp 账号，确认消息费用承担方，验证发送与状态回调。
4. 配置买家同意记录来源、发送模板、静默时段、客服联系方式与知识库。
5. 在测试订单上预览工作流，分别演练付款停止、退订、人工接管和失败处理。
6. 通过启用检查后，授予一次性试用额度并开放真实自动化；条件不满足时展示具体阻塞项。

首版一个 WhatsApp 业务号码只绑定一个店铺，避免入站会话无法确定所属店铺。已有账号能否与其他客户端共存须按实际接入方式验证，不默认支持。

### 3.2 工作台页面

| 页面 | 必须可见的信息与操作 |
| --- | --- |
| 总览 | 接入状态、待处理订单、待人工会话、额度、真实效果；无数据时给出空状态 |
| 店铺与通道 | 授权状态、权限范围、最近同步时间、模板状态、测试结果、解绑 |
| 工作流 | 触发条件、时间、消息预览、静默时段、频次上限、启停、规则版本 |
| 订单 | 原平台状态、同步时间、工作流状态、消息结果、COD 确认结果、原平台链接 |
| 会话与人工队列 | 买家语言、回复窗口、接管状态、负责人、知识来源、关联订单、客服操作记录 |
| 知识库 | FAQ 与商品来源、更新状态、冲突项、管理员审核记录 |
| 财务中心 | 订阅有效期、Credits 分类余额、逐笔流水、USDC 付款状态与异常申诉 |
| 报表与设置 | 指标口径、样本与观察窗口、成员权限、数据导出和删除申请 |

消息须区分排队、平台已接受、已发送、已送达、已读、失败、结果未知。平台接受请求不能显示为已送达。只在已有真实回调时显示已读。

### 3.3 系统责任划分

采用 Next.js 16 App Router 全栈架构：页面与 Route Handlers 位于同一应用，服务端业务、数据访问和第三方适配集中在 `lib/server/**`。本节是目标架构，不代表仓库已实现相关服务；后续编码前须遵循仓库 `AGENTS.md`、[API 接口契约](API.md) 并查阅当前安装版本的 Next.js 文档。

| 模块 | 责任 | 权威数据或依赖 |
| --- | --- | --- |
| Web 页面与客户端交互 | 授权配置、业务操作、消息与财务状态展示 | Server Components、必要的 Client Components |
| Next.js Route Handlers | 浏览器 HTTP、第三方回调、输入校验、认证和响应映射 | `app/api/v1/**/route.ts`；Web Request / Response |
| 服务端领域层 | 资格判断、订单、会话、知识、计费和报表规则 | `lib/server/**`；不能被客户端代码导入 |
| 平台适配器 | 验签、字段映射、状态同步、授权撤销处理 | WooCommerce / WhatsApp 官方 API 与 Webhook |
| 工作流与任务 | 调度、取消、频次限制、规则版本和补偿 | PostgreSQL 业务状态；BullMQ + Redis 持久队列 |
| 会话与 Agent | 入站处理、知识检索、事实校验、人工接管 | 已审核知识与平台查询结果 |
| 支付与额度 | 支付订单、链上校验、补偿、订阅与额度记账 | Solana RPC；PostgreSQL 财务账本 |
| 报表与审计 | 指标归因、数据质量、操作和决策记录 | 持久化业务事件 |

PostgreSQL 保存业务状态和财务流水；Redis 不作为余额或付款结果的唯一来源。支付、赠送、扣费、释放预留和退款调整均采用可追溯流水。业务状态变化与待执行事件须可靠保存，进程重启后可以恢复。Server Components 直接调用服务端领域层，不从服务端绕行本应用 HTTP API；浏览器、轮询与第三方系统通过 Route Handlers 访问。

## 4. 平台接入与消息发送条件

### 4.1 平台能力与验证表

| 平台 | 计划接入对象 | 买家联系数据 | 付款与履约状态 | 启用条件 |
| --- | --- | --- | --- | --- |
| WooCommerce | 已创建订单、商品、订单更新 | 经商家授权读取订单字段；同意记录须另外证明 | 从订单当前状态和已验证的支付方式映射；COD 单独识别 | 测试店跑通真实样例与权限撤销；记录版本、网关和插件 |
| Shopify | Order、AbandonedCheckout、商品 | 姓名、电话等受保护字段按实际访问批准范围使用 | checkout 与 order 分别处理；关联字段随 API 版本验证 | GraphQL 权限、字段可用性、恢复链接、付款关联均通过 |
| TikTok Shop / Shopee / Lazada | 经目标市场允许的订单与客服资源 | 是否完整、是否脱敏及用途限制逐项验证 | 事件、恢复链接和可写能力逐项验证 | 获得官方接入并完成目标国家、店铺类型的端到端验证 |

WooCommerce 的 order.created、order.updated、order.deleted 是平台事件；付款与 COD 需要解析实际订单数据，不假设存在通用 payment.failed 事件。[WooCommerce 官方 Webhook 文档](https://developer.woocommerce.com/docs/apis/rest-api/v3/webhooks)

Shopify 的弃购结账与 Order 是不同对象，客户字段访问也有专门要求。[Shopify AbandonedCheckout](https://shopify.dev/docs/api/admin-graphql/latest/objects/AbandonedCheckout)、[受保护客户数据要求](https://shopify.dev/docs/apps/launch/protected-customer-data)

每次新增适配器必须记录 API 版本、国家、权限、事件样本、字段缺失策略、限流与撤销行为。接入文档可读取不等于商户已获权限；没有实测证据的能力不能出现在“已支持”列表。

### 4.2 内部业务事件与同步规则

以下是产品内部事件名称，不是所有平台通用的原生 Webhook：

| 内部事件 | 含义与处理 |
| --- | --- |
| checkout.eligible | 已取得必要联系信息的未完成 checkout；首版不启用 |
| order.created / order.updated | 更新原平台订单快照，重新判断工作流 |
| order.paid | 原平台确认付款，停止本订单催付 |
| order.cancelled / order.fulfilled / order.deleted | 取消、已发货或源订单删除，停止不适用的提醒与 COD 等待 |
| order.delivery_result | 经物流或商家核实的最终履约结果；无数据时标记未知 |
| message.inbound / message.status | 买家入站消息与平台发送结果 |
| consent.changed / conversation.handoff | 退订或人工接管，撤销不适用任务 |
| payment.observed / payment.settled | 找到候选交易与完成验证入账，二者分开 |

事件保存租户、店铺、平台对象、平台事件标识、事件时间、接收时间和处理结果。Webhook 验签通过后先可靠持久化，再确认接收；重复事件不重复产生业务作用。平台事件标识缺失时使用适配器定义的稳定去重键。

旧事件不能把已付款订单退回待支付。状态冲突或无法排序时查询原平台；失败期间暂停该订单自动化。执行发送前再次查询当前订单，查询失败不发送。补偿同步只恢复状态，首次绑定时导入的历史订单默认不批量催付。

### 4.3 WhatsApp 同意、模板与回复窗口

主动联系买家前必须已有有效同意记录，并按用途使用获批模板；自由形式回复受最近买家消息开启的 24 小时客户服务窗口限制。买家退订必须被执行。[WhatsApp 官方消息政策](https://whatsappbusiness.com/policy/)

首版发送条件：

1. 买家提供有效联系方式，且同意范围覆盖本次用途；订单留存电话本身不视为营销同意。
2. 同意记录包含店铺、联系方式、用途、文案版本、采集来源、时间和撤回状态。可通过商户结账勾选与受支持的数据接入采集，不默认预勾选。
3. 主动催付、COD 首次确认和二次提醒统一使用当前获批模板，语言、参数和用途与审核结果一致。
4. 催付与弃购提醒按 Marketing 用途准备；COD 模板只包含订单确认信息，不混入促销。最终类别以平台审核结果为准。
5. AI 回答只在有效回复窗口内发送；买家每次入站消息更新该窗口。窗口关闭后暂停自由回复，并使用相应用途的获批模板或提示人工处理。
6. 识别明确退订请求和常见语言表达；不确定时停止主动自动化并进入人工队列。首版全量退订停止所有主动提醒，重新启用须有新的同意证据。
7. 工作台可全局暂停店铺自动化；暂停、解绑、模板失效或通道撤销立即影响排队任务。

首版默认按买家已知时区，缺失时按店铺时区，设置 21:00～09:00 为主动提醒静默时段。入站咨询仍可在有效窗口内回复。静默规则不扩大发送资格；延迟后超出工作流有效期的任务直接停止。

频次按“租户 + 店铺 + 买家联系方式”计算，滚动 24 小时内主动提醒最多 2 次，跨订单、跨工作流合并限制。额度被占满时记录抑制原因，不重复排队制造发送风暴。

### 4.4 接入故障与安全停止

| 情况 | 系统行为 |
| --- | --- |
| 电话缺失、格式错误、无法送达 | 标记缺失或通道不可达，不判定为恶意买家 |
| 模板未批准、暂停、拒绝，账号权限失效 | 停止相关工作流，通知商户修复 |
| 平台限流、可确认未受理的临时错误 | 指数退避，最多 3 次发送尝试；每次重新检查资格 |
| 请求超时、平台是否受理未知 | 记录结果未知，保留关联标识与额度预留，查回调或运营复核；不能盲目重发 |
| 订单、同意或通道状态无法确认 | 安全停止，并说明原因 |
| 店铺解绑或授权撤销 | 禁止新任务，撤销排队任务；已交平台的消息保留记录 |

无法召回已经交给平台发送的消息；界面须区分可取消任务与已提交消息。发送与停止操作按同一买家串行协调，提交前复查停止状态。执行后才发生的付款、退订或接管不能被描述为成功撤回。

## 5. 订单工作流与会话 Agent

### 5.1 场景 A：已创建未支付订单提醒

**触发对象**：首版仅处理非 COD、尚未付款且未取消或发货的 WooCommerce 订单。支付状态映射由适配器样例证明；on-hold 等状态不能不加判断地当作付款失败。

**时间规则**：

- 首次提醒计划时间为原平台订单创建时间 + 15 分钟。
- 到时复查订单、联系方式、同意、模板、人工状态、订阅、额度和频次上限。
- 实时事件迟到且订单年龄不超过 2 小时时可按当前资格执行；超过 2 小时停止首次提醒并记录事件迟到。
- 二次提醒默认关闭。商户开启后，在首条提醒送达 6 小时后复查并尝试一次；订单创建满 24 小时后终止本工作流。
- 静默时段导致延期时重新判断有效期；不得承诺所有订单都在第 15 分钟送达。

**消息与后续**：

1. 发送已批准的本地语言模板，使用原平台允许的订单付款链接。
2. 首版默认不提供自动优惠。仅允许管理员预先配置且平台核实有效的活动；模型不能决定折扣，失效优惠不得发送。
3. 短链只跳转到已授权店铺的允许域名与平台恢复地址，使用不可猜测标识；不在 URL 中暴露电话和地址。
4. 买家回复进入场景 C；付款、取消、发货、退订、接管、规则停用或授权撤销终止后续自动提醒。
5. 付款时记录真实平台对象关联和时间；不能用短链点击替代付款证据。

工作流状态与电商订单状态分别保存：

| 状态 | 含义及后续 |
| --- | --- |
| scheduled | 等待首次或二次提醒；到时重新检查 |
| awaiting_delivery | 平台已受理，等待送达结果；不重复发送 |
| delivered | 确认送达；符合条件时允许安排二次提醒 |
| suppressed | 因静默、缺失授权、频次等未发送，保存原因和是否可恢复 |
| handoff | 等待人工；本买家所有自动化暂停 |
| stopped | 付款、取消、发货、到期或永久不可发送，记录终止原因 |
| delivery_unknown / failed | 发送结果未知或明确失败，分别进入核查或有限重试 |

### 5.2 场景 B：COD 发货前意愿确认

**触发对象**：原平台已创建、明确使用 COD、尚未发货的订单。首条确认在创建后 5 分钟进入发送资格检查；遇静默或缺少同意时不得强行发送。

消息展示实际商品、金额和商家已有的预计发货时间；无法核实时间时不写“明天发出”。提供“确认收货意愿”“申请修改地址”“申请取消”三个动作，强调申请结果由商户确认。

| 买家行为或结果 | 本产品状态 | 商家处理与回写边界 |
| --- | --- | --- |
| 明确确认 | confirmed | 保存证据并通知商家；不自动创建发货单 |
| 申请改址 | address_change_requested | 暂停本订单自动确认，核对申请人、地址及运费，由商家在原平台操作 |
| 申请取消 | cancellation_requested | 暂停催付和确认，由商家审核；收到原平台取消状态才显示已取消 |
| 12 小时未回复 | no_response | 二次提醒默认关闭；开启后仅在发货截止前、频次与授权允许时提醒一次 |
| 联系数据错误或消息失败 | contact_unreachable | 展示原因，进入人工联系；不自动提高欺诈等级 |
| 已发货、商家决定继续履约或达到截止时间 | closed | 结束自动确认，记录商家决定与原因 |

商家必须设置实际的发货截止时间。截止前未确认的订单进入人工队列，不无限等待。达到截止时间不自动取消或拦截；工作台显示“未确认，需商家决定”，不能显示为平台已暂停发货。

改址或取消处理须记录负责人、原平台结果和操作时间。原平台不允许改址、订单已发货或运费发生变化时，由人工说明并与买家确认。买家确认只证明表达的收货意愿，不证明地址真实或最终一定签收。

### 5.3 场景 C：买家咨询与本地化回答

入站消息经验签、去重和店铺路由后进入会话。未关联订单的买家可咨询公开商品和 FAQ；查询订单详情、改址或取消须完成店铺设定的身份核对，不能仅凭另一人的订单号披露信息。

- 优先使用买家明确选择的语言，其次使用可信的会话或店铺语言信息；不能只按国籍决定语言。
- 首版覆盖印尼语常见缩写及英语表达，例如 bisa COD?、ongkir brp?；不把印尼语缩写混称为爪哇语。
- 商品说明与 FAQ 使用商家审核内容；库存、价格、优惠资格和履约时间在答复前查询最新可信来源。
- 首版仅在确认商品、数量和配送地区后回答可验证运费；条件不全时说明需要确认。
- 商品静态信息每 15 分钟增量同步一次；需要实时值的查询失败、冲突或无来源时，不作确定承诺并交人工。
- 模型输出经结构检查、允许动作检查和事实来源校验后才能发送；JSON Schema 不替代事实校验。
- 买家、商品描述和检索内容中的指令不能修改系统权限、额度、价格或工作流。
- 每个计费窗口最多 20 条自动出站消息，含模板与 AI 回复；达到上限后转人工，不自动开新窗口追加扣费。

### 5.4 人工接管

以下情况进入人工：买家要求客服，投诉或退款，改址或取消申请，商品事实无法核实，身份关联不确定，消息或模型持续失败，达到自动消息上限，以及商户主动接管。

| 会话状态 | 规则 |
| --- | --- |
| automated | 在发送条件与额度允许时自动处理 |
| waiting_human | 原子暂停本买家在该店铺的 AI 回复和自动提醒，进入队列 |
| human_active | 由一名客服占有处理权，其他成员可以查看和交接 |
| resolved | 保存处理结果；继续停止自动化，直到明确恢复或出现经规则允许的新会话 |

新消息在接管期间只提醒客服，不触发 AI。无人在线时展示已配置的工作时间和可用客服渠道；最多发送一次符合当前窗口规则的接管提示，不承诺已有人即时接单。买家须有清晰可达的人工联系入口。

恢复自动化须由有权限成员执行，并重新检查付款、发货、退订、窗口和规则有效期；已失效的旧提醒不补发。接管通知、规则暂停和失败记录可追溯到具体事件与负责人。


## 6. Credits、订阅与 Solana Pay

### 6.1 统一计费单位

**1 Credit = 同一租户、同一店铺、同一买家，在一个固定 24 小时计费窗口内的自动化服务额度。**

计费窗口从首次自动出站消息被确认送达的时间开始，到该时间 +24 小时结束。窗口内的订单提醒、COD 确认和 AI 回复共享 1 Credit，每窗口最多 20 条自动出站消息。跨店铺分别计算；同店铺多个订单共享当前窗口。

计费窗口与 WhatsApp 客户服务窗口分开：前者由首条自动消息送达启动，后者由最近买家入站消息更新。买家继续回复不延长本产品固定的计费窗口，也不自动产生新收费。

| 行为或状态 | Credits 规则 |
| --- | --- |
| 准备开启新的计费窗口 | 原子预留 1 Credit；没有可用额度则停止自动发送并提示商户 |
| 首条自动消息确认送达，或更强的已读证据先到 | 将预留转为消耗，建立窗口；API 受理或 sent 不视为送达 |
| 无买家回复但已送达 | 消耗 1 Credit，费用覆盖已完成的触达服务 |
| 同窗口后续消息、多工作流、重复回调 | 不重复扣 Credit；共享 20 条自动消息上限 |
| 明确失败且确认未送达 | 释放预留；有限重试不额外扣 Credit |
| 发送结果未知 | 额度保持预留并标明原因；24 小时无终态升级复核，不能以超时认定未送达 |
| 纯人工发送或回复 | 不消耗 Credits；仍遵循通道发送规则和第三方收费 |
| 超过窗口后需要新的自动服务 | 再次检查资格并预留 1 Credit；不会仅因时间经过自动续扣 |
| 达到自动消息上限 | 停止 AI 并转人工，本窗口不再创建收费窗口 |

同一买家的窗口创建和送达处理必须防并发，重复消息回调不能产生多个窗口。单条消息先读后达、先达后 sent 等乱序回调按已有最强证据处理。超时复核结果仍不能确认时，保持可解释状态；有真实送达证据后只扣一次。错误扣费使用补偿流水，不能直接改历史记录。

### 6.2 额度与订阅有效期

- **试用**：首次完成真实店铺和通道启用检查后，赠送 100 Credits，有效期 30 天，期间可体验首版完整工作流和一个店铺。同一已验证店铺和商户身份不能重复领取。
- **月度套餐额度**：随当期订阅发放，只在对应周期有效，不结转。月付周期按 UTC 生效时间到次月同日同时间；缺少同日时取该月最后一天。
- **加购额度**：入账后有效期 12 个自然月；购买 Credits 不自动延长订阅，不解除店铺或功能限制。
- **消耗顺序**：优先使用最早到期的可用额度。预留记录绑定原额度批次；期限内预留且期限后才送达的消息仍从该批次结算。
- **余额展示**：分别显示可用、预留、已消耗、过期和补偿，能查看每笔所属窗口、订单、消息和原因。
- **到期或余额不足**：停止新自动化及排队任务；继续提供既有记录和人工队列。人工发送仍须满足通道条件，不暗示其没有 Meta 费用。
- **续费**：首版为用户主动支付。提前购买同套餐续费从原到期时间延长；过期后购买从本次入账生效。新周期额度到该周期开始才发放。
- **套餐变更**：首版只在下一周期生效，不提供自动按比例升降级。新周期开始时检查店铺上限，超限由商户选择保留店铺；未选择则停止超限店铺自动化并提示处理。

试用无需先购买本产品或绑定本产品付款方式；商户仍需完成 WhatsApp 接入和其适用的通道计费设置。

### 6.3 第三方费用与定价测算

首版要求商户自己的 WhatsApp 账号具备有效计费安排。Meta 或 BSP 消息费用由商户依其账单承担，与本产品订阅和 Credits 分开。若实际接入模式要求 SolaFlow 代付，必须重新测算并更新价格条款后才能开放该模式。

WhatsApp 的收费与接收市场、消息类别和实际送达相关，弃购提醒属于 Marketing 使用场景；不能把所有对话视作相同外部成本。[WhatsApp 官方价格与类别说明](https://whatsappbusiness.com/products/platform-pricing/)

以下保留原定价作为内测测算方案，正式发布前需结合模型、基础设施、运营成本和商户反馈确认。金额按 USD 标价，首版支付报价按 1 USD 标价单位对应 1 USDC 生成；不提供 USDC 兑换或法币赎回保证。

| 套餐 | 每月标价 | 当期 Credits | 店铺上限 | 功能范围 |
| --- | --- | --- | --- | --- |
| Starter | 29 USDC | 1,000 | 1 | 待支付提醒、基础咨询、人工接管、基础报表 |
| Growth | 79 USDC | 3,500 | 3 | Starter 能力、COD 确认、自定义语调与规则 |
| Enterprise | 199 USDC 起，按合同报价 | 基础方案 10,000 | 基础方案 10 | 多成员权限、容量与支持级别按合同约定 |

点数加购基准为 0.02 USDC / Credit，100 Credits 起购且数量必须为整数。例如 50 USDC 对应 2,500 Credits。首版不开放任意金额自动折算、无上限店铺、自动阶梯折扣、独立号段或未经落实的专属服务承诺。

财务中心在购买前展示套餐、权益、到期规则、收款网络、代币、金额、余额不足处理和费用边界。工作流启用页说明模板类别和第三方费用；读取不到真实单价时显示“需查看通道账单”，不生成虚构估价。

| 成本项 | 需要采集的数据 |
| --- | --- |
| LLM | 每窗口调用次数、输入输出用量、供应商实际价格、失败重试 |
| 基础设施 | 租户和窗口分摊的数据库、队列、RPC、日志等费用 |
| 支持与运营 | 接入指导、人工复核、故障处理及套餐承诺的服务成本 |
| 通道 | 商户实际 Meta / BSP 账单；即使不计入本产品成本，也计入商户 ROI |
| 商户收益 | 经验证的增量订单收益，减去优惠、消息费及新增履约成本 |

每种套餐至少按低、常规、高使用量测算。毛利以实际收入减去实际服务成本计算；没有测量前不发布“低费率”“一定盈利”结论。充值前展示网络费由谁承担；普通钱包付款通常还需要 SOL 网络费，首版不承诺免 gas。[Solana 交易费用说明](https://solana.com/docs/core/fees)

### 6.4 支付订单与钱包流程

首版仅支持指定 Solana 网络上的原生 USDC，开发环境与正式环境的支付订单、代币配置和 Credits 账本完全隔离。主网和 devnet 的 mint 从 Circle 官方资料核对并加入服务端允许列表，不能按代币名称或用户提交的 mint 判断。[Circle USDC 地址资料](https://developers.circle.com/stablecoins/usdc-contract-addresses)

1. 用户选择套餐、续费或整数点数数量，服务端按当前价格版本建立支付订单。
2. 支付订单固定租户、用途、网络、USDC mint、收款地址、精确金额、权益快照、唯一 reference、创建时间和 20 分钟报价有效期。
3. 服务端生成 Solana Pay URL 与二维码；页面另提供钱包连接和签名流程，不能把生成二维码等同于已完成钱包集成。
4. 签名前展示网络、代币、收款地址、金额和预计费用；支持拒签、余额不足、钱包不兼容和交易过期状态。
5. 通过 reference 查找候选交易，读取链上结果并校验。浏览器回调、截图和用户提交的 Signature 仅是查询线索。
6. 候选交易达到 confirmed 且通过初步校验时显示“已检测到付款，等待最终确认”；Credits 暂不可用。
7. 同一交易达到 finalized 并通过完整校验后，在一次数据库事务内登记转账、支付订单与额度或订阅权益，显示“余额可用”。
8. 页面关闭后仍持续追踪，用户重新打开可以看到一致结果；正式环境的交易提供对应网络浏览器链接。

Solana Pay 的 reference 用于交易查找，服务端仍须验证转账；confirmed 与 finalized 有不同含义。[Solana Pay 支付验证](https://solana.com/docs/tools/solana-pay/quickstart/transfer-requests)、[Solana RPC 确认级别](https://solana.com/docs/rpc)

### 6.5 链上校验与一次入账

入账前必须同时满足：

- 支付订单属于当前服务端记录的租户，网络与环境匹配。
- 交易结果成功，确认级别为 finalized。
- 转账是允许的 USDC mint、正确代币程序下的有效转账；转入受配置收款方控制的正确代币账户。
- 实收金额与该订单精确金额完全一致，按代币最小单位计算，不使用浮点比较。
- reference 属于本支付订单，且该转账尚未用于其他订单入账。
- 付款链上时间在报价有效期内；缺失可信时间的转账进入复核，不能用监听到达时间替代。

同一“网络 + Signature + 转账位置”只能产生一次权益；一个支付订单最多完成一次自动结算。MVP 每张支付订单接受一笔满足完整金额的转账，不自动合并多笔少付，不将同一笔转账重复分配。

支付订单结算、转账唯一占用、财务流水与权益更新须原子提交。RPC 监听、定时补偿和人工核查走同一校验入口，并受相同去重约束；缓存锁不作为唯一保证。

发现一个 reference 下有错误或失败交易时，记录该候选结果并继续检查其他交易，不能让第一笔无效交易阻断后续有效付款。

### 6.6 支付异常、补偿与退款

| 状态或异常 | 产品行为 |
| --- | --- |
| awaiting_payment | 等待付款，展示报价有效期 |
| detected | 已发现候选交易，继续验证 |
| confirming | 已通过初步检查，等待 finalized |
| credited | 验证并入账完成；记录完整证据 |
| expired | 未发现期限内有效付款；保留订单以便处理迟到证据 |
| review_required | 少付、多付、重复支付、有效期外付款、时间缺失或其他不匹配，暂不自动入账 |
| 交易失败或错误候选 | 记录候选失败；支付订单在有效期内仍可等待正确付款 |
| 超时后才发现期限内有效转账 | 依链上付款时间和同一校验规则结算，不因为监听迟到拒绝入账 |
| RPC 不可用或确认持续未完成 | 保持处理中，切换备用 RPC 并补偿；不要求用户再次付款 |
| confirmed 候选随后失去链上确认 | 回到核查状态；因尚未授予可用权益，不提前创造余额 |

监听和补偿每分钟扫描未结算订单；超过 5 分钟仍待确认提示用户，超过 30 分钟升级运营核查。以上时间是提示与核查阈值，不是区块链必然到账承诺。

用户申诉需选择支付订单并提交 Signature；不能修改订单金额或以客服按钮绕过校验。平台级入账调整仅由有权限的财务人员提出，另一名复核人员确认，保留理由和前后余额。商户财务角色不能给自己的余额手工加点。

首版退款走人工核实流程。必须核对付款归属、可退款权益和有效收款地址；退款申请冻结相关未消耗权益，确认链上退款后用新流水冲销。地址不能仅凭聊天消息确定，也不能假定交易发送地址就是可退款地址。已消耗部分按服务条款和适用规则处理，客服不能承诺无条件全额退款。

链上收款与退款的签名凭证由独立财务安全机制管理，不进入浏览器、模型或仓库；首版不在 SaaS 内自动签署退款交易。既有交易与财务流水不可删除或覆盖。

## 7. 权限、数据与可靠性要求

### 7.1 权限与租户隔离

所有店铺、联系人、订单、会话、知识库、支付订单和额度流水都必须归属租户。服务端通过认证会话确定租户，不能信任客户端传入的 tenant_id。所有资源读取、导出、修改和异步任务均检查租户归属；平台级处理单独授权和审计。

| 操作 | 所有者 | 管理员 | 客服 | 商户财务 |
| --- | --- | --- | --- | --- |
| 店铺与通道绑定、规则和知识配置 | 允许 | 允许 | 不允许 | 不允许 |
| 会话查看与人工处理 | 允许 | 允许 | 仅授权店铺与分配队列 | 不允许 |
| 购买服务、查看财务与申诉 | 允许 | 不允许 | 不允许 | 允许 |
| 成员邀请、授予财务权限、租户删除 | 允许 | 仅可管理客服成员 | 不允许 | 不允许 |
| 手工充值入账、平台退款执行 | 不允许 | 不允许 | 不允许 | 不允许 |

成员同时承担多个角色时按明确授予的权限合并，不能因“管理员”名称默认获得资金权限。客服不能自行增加店铺权限或授予财务角色。

平台支持访问须记录授权原因、租户、范围、人员、时间和操作；常规排障优先使用脱敏状态。店铺密钥和 WhatsApp 凭证加密保存，不返回前端明文。日志、错误页面和导出不含 Token、私钥或完整敏感字段。

### 7.2 数据保留与删除

以下是默认产品保留策略；正式市场如有适用要求，须在启用前调整并披露，不把本表视为法律结论。

| 数据 | 默认保留与控制 |
| --- | --- |
| 订单联系数据与会话正文 | 业务结束后最多 90 天；商户可提前申请删除 |
| 同意、退订和业务审计 | 最多 12 个月；保留证明和最小化匹配信息，不保留无关内容 |
| 财务流水 | 按服务主体的财务留存要求确定；商业发布前明确期限与说明 |
| 灾备副本 | 滚动保留最多 30 天，访问受限；恢复时重放删除清单 |

在适用规则允许的范围内，仅保留履行退订所需的最小化抑制标识，避免删除联系人后又重新导入并发送；若须完全删除该标识，新采集数据必须重新验证同意，不能沿用旧授权。

数据删除申请立即停止相关自动化，30 天内完成可删除数据清理。受必要留存约束的数据须说明原因、范围和期限。解除店铺绑定立即撤销凭证和任务，不自动清除依法或依合同需留存的财务记录。

发送给模型的数据限于回答所需内容；选择和配置供应商时确认数据使用与保留安排，不默认允许其训练使用。公开链上 memo、reference 关联文案和 URL 不写入买家姓名、电话、地址或会话正文。

### 7.3 服务目标与故障行为

这些是首版验收目标，按实际测试记录，不能替代外部平台或链上结果：

| 项目 | 目标与计时口径 |
| --- | --- |
| Webhook 接收 | 正常负载下，从进入服务到可靠持久化并响应的 P95 ≤2 秒 |
| 定时任务执行 | 全部发送条件满足时，计划到期到向网关提交请求的 P95 ≤60 秒 |
| 买家首次自动回复 | 可答复且窗口、额度允许时，从入站持久化到提交回复的 P95 ≤10 秒 |
| 停止与人工接管 | 停止事件持久化后 5 秒内影响调度；消息提交前最后检查，已提交消息按 4.4 记录 |
| 充值检测 | RPC 正常时，从链上 finalized 事件时间到服务发现有效转账的 P95 ≤60 秒 |
| 本地入账 | 完整验证成功到可用权益事务提交的 P95 ≤2 秒 |
| 可用性 | 商业发布后月度自身服务目标 99.5%；外部故障分开记录，用户可见失败仍须统计 |

首轮负载验收使用 20 个租户、每分钟 60 条业务事件和 10 个并发入站会话，持续 30 分钟；同时检查排队增长、重复任务、余额一致性和跨租户隔离。该规模只证明内测容量，不支持“无限制”宣传。

监控至少覆盖：Webhook 验签失败、处理延迟、队列积压、重复发送、模板失效、模型错误、接管超时、支付异常、入账去重冲突、额度预留长期未释放和账本不平。LLM 故障时不生成无来源答复；Redis 故障停止新自动化；数据库故障不发送无法记录的消息、不授予无法记账的权益。

### 7.4 数据质量与验收证据

每项验收保存环境、时间、输入、关键事件、实际结果和脱敏证据。分别记录模拟、devnet、真实店铺、真实 WhatsApp 和主网付款结果。测试 USDC 不能生成正式 Credits，页面不得把测试交易显示为真实收入。

对外报告只引用真实数据；缺失物流、付款或消息终态时显示未知。图表必须能查看指标口径、样本量、排除项和更新时间。种子商户数量、业务增长和毛利未经确认不能写成上线成果。

## 8. 验收标准

### 8.1 核心业务与财务验收

以下案例是验收要求，不表示已经执行。每项给出可复现输入与结果；正常链路和异常链路必须同时通过。

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| AC-01 | 绑定真实 WooCommerce 测试店，接收合法及伪造 Webhook | 合法事件可追溯，伪造请求拒绝且无业务作用 |
| AC-02 | 未同意营销、电话缺失、模板未批准的待支付订单 | 不发送催付，展示具体抑制原因 |
| AC-03 | 非 COD 订单待支付满 15 分钟且全部资格满足 | 只提交一次有效模板，参数与原平台一致 |
| AC-04 | 买家在第 14 分钟付款，付款事件迟到 | 发送前查询发现已付，不提交提醒 |
| AC-05 | 同一 Webhook 重放 10 次，夹杂旧状态 | 不重复生成业务作用，订单不从已付回退 |
| AC-06 | 买家退订或商户暂停后仍有排队任务 | 后续任务停止；已提交消息如实标记 |
| AC-07 | 静默、滚动频次上限、订单有效期冲突 | 按条件延期或终止，不超上限补发 |
| AC-08 | COD 确认、改址、取消、12 小时未回复 | 各状态与人工任务正确，不擅自写入平台取消或发货状态 |
| AC-09 | 同一通道联系失败但订单仍有效 | 仅标记通道不可达，不判定恶意或自动取消 |
| AC-10 | 人工接管与 AI 回复并发、新消息继续到达 | 提交前遵守停止状态，接管后只提醒客服 |
| AC-11 | 输入不存在库存、未经批准折扣、商品中的恶意指令 | 不作未验证承诺，不修改系统规则和权限 |
| AC-12 | 同买家并发首条消息、重复及乱序送达回调 | 同店铺单窗口只消耗 1 Credit，跨店铺分别计算 |
| AC-13 | 明确失败、结果未知、人工回复、窗口到期 | 按 6.1 释放或保留预留，人工不扣点，不自动续扣 |
| AC-14 | 余额为零或订阅到期时任务继续出队 | 停止新自动化，不产生负余额 |
| AC-15 | 到期批次已有预留、续费提前购买、超店铺上限 | 额度批次结算与新周期发放正确，超限店铺有明确停止状态 |
| AC-16 | devnet USDC 支付完整流程 | 验证并只增加测试权益，正式账本不受影响 |
| AC-17 | 正确支付先达到 confirmed 后 finalized | 前者仅显示检测到；后者授予可用权益 |
| AC-18 | 监听、补偿和人工核查并发处理同一有效转账 | 只形成一次支付结算和一组权益流水 |
| AC-19 | 金额少付或多付、错误 mint、收款方或网络 | 不自动授予权益，候选结果和复核原因可见 |
| AC-20 | 先向同一 reference 提交无效交易，再提交正确交易 | 无效候选不阻断正确付款验证 |
| AC-21 | 报价期限内付款但延迟发现，或期限外付款 | 前者按链上时间结算，后者进入复核 |
| AC-22 | RPC、进程中断后恢复，用户关闭付款页面 | 支付状态可恢复，补偿不重复入账，不要求重复付款 |
| AC-23 | 用户拒签、缺少 USDC 或 SOL、钱包不兼容 | 可解释且可恢复，不显示虚假的支付成功 |
| AC-24 | 租户 A 猜测租户 B 的资源 ID、导出地址或支付订单 | 服务端拒绝访问，余额及业务数据不泄漏 |
| AC-25 | 店铺解绑、权限撤销、删除申请后任务恢复 | 凭证和任务不能重新激活；删除与保留结果可追溯 |
| AC-26 | 有效期内没有付款或物流结果，样本不足 | 显示未知或观察中，不制造 KPI 达成 |
| AC-27 | 主网真实小额 USDC 充值与异常付款复核 | 有真实链上与账本对应证据，适用于正式付款门槛 |
| AC-28 | 退款申请、权益冻结、真实退款确认及重复回调 | 仅授权流程可处理，一次冲销，原支付与账本证据保留 |

### 8.2 语言与人工处理验收

首版评测集至少 100 条，由印尼语与英语真实使用者复核，覆盖商品、运费、COD、俚语、混合语言、歧义、投诉、退订和提示注入。测试数据去标识化，区分标准回答、需要澄清和必须人工处理。

- 有明确知识来源的回答正确率目标 ≥95%；逐题记录错误，不仅看平均分。
- 越权操作、泄露其他买家信息、编造价格库存优惠或发货承诺出现任一例，视为发布阻断。
- 明确退订、要求人工、退款投诉必须进入规定路径；漏处理任一例，修复后重测对应类别。
- 未关联订单和多订单歧义须先澄清，不猜测买家身份或订单。
- 工作台人工队列、语言显示、接管、交接与恢复需由商户完成一次真实演练。

### 8.3 商业发布门槛

自动化内测前必须完成 AC-01～AC-15、AC-24～AC-26、语言评测及真实 WhatsApp 送达和回复验证。测试充值开放前完成 AC-16～AC-23。

正式收取服务费前还须满足：

- 主网、原生 USDC mint、收款方与账本配置核对完成，AC-27、AC-28 通过。
- 钱包签名、真实入账、恢复和复核流程有独立证据；测试成功不能替代主网成功。
- 通道费用承担方、正式价格、退款条款、财务留存期限和隐私说明落实。
- 基本人工处理、值班责任、故障告警、账本对账和备份恢复可执行。
- 无未解决的重复发送、错误入账、越权访问、退订失效或资金凭证泄露问题。

业务 KPI 不作为技术通过的替代证明。所有商业目标未达成时如实报告；技术验收通过也不直接证明有业务增量。

## 10. 风险与能力变更

| 风险 | 处理要求 |
| --- | --- |
| 买家同意不足、模板拒绝或账号受限 | 关闭受影响工作流，保留抑制原因；修复后重新检查，不能转非官方路径绕过条件 |
| 平台客户字段、事件或站外链接限制 | 按国家、店铺和 API 版本核验；不可用时明确显示不支持 |
| 规则重复执行或状态迟到 | 去重、最新状态查询、取消任务、补偿与事故复盘 |
| AI 错误承诺、提示注入和身份混淆 | 事实校验、只读边界、人工处理、评测阻断 |
| 通道费用或模型成本变化 | 更新测算与价格版本；已生成有效报价按固定快照处理 |
| 付款异常、RPC 故障或重复入账 | 候选校验、唯一转账占用、事务记账、主备 RPC 和复核 |
| 商户缺少 USDC 使用能力 | 记录真实采用阻力，提供网络与费用说明；不暗示用户必须立即获取加密资产 |
| 非官方 WhatsApp 方案不稳定 | 保持研究状态；不能对外承诺可靠性或官方支持 |
| 数据、访问权限与市场要求变化 | 权限回收、最小化数据、更新保留和隐私安排，重新执行受影响验收 |

Baileys 项目自述其没有 WhatsApp 官方授权或关联；扫码方案需独立评估，不与 Cloud API 交付混为一项。[Baileys 项目说明](https://github.com/WhiskeySockets/Baileys/blob/master/README.md?plain=1)

后续新增平台、语言、代币、自动退款或周期扣款时，必须更新范围、价格、权限、异常规则与验收案例，不能仅添加界面入口。
